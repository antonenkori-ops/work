# Work Assistant

Внутренний рабочий инструмент: Jira-дашборд, диаграммы Ганта, алерты AlertManager, генератор планов работ.
Backend — Python (FastAPI) + SQLite, frontend — React (Vite). Без Docker, всё поднимается напрямую на рабочей машине.

## Этап 1: Jira-дашборд

Что реализовано:
- Синхронизация задач и комментариев из Jira по кнопке «Обновить» (без фонового опроса).
- Локальное хранение в SQLite (`backend/work_assistant.db`, создаётся автоматически).
- Список задач в работе (не Done), сортировка по дате обновления, описание и комментарии свёрнуты по умолчанию.
- Статистика: всего выполнено / с начала года / за месяц / за неделю (по дате резолюции).

## Этап 4: Релизы (генератор планов работ)

Раздел меню «Релизы» — создание Плановых релизов по образцу `наброски/План работ.xlsx`:
- Новый Плановый релиз копирует стартовый набор пунктов/рисков/наборов модулей из примера
  (Web-сайт Сбербанка + SberCraft); дальше пункты правятся/добавляются/удаляются.
- Даты пунктов считаются каскадом от «Начала раздела» через длительность и зависимости.
- Общие наборы модулей (site/sbercraft) на уровне релиза — правите список в одном месте,
  все ссылающиеся на него пункты подтягивают изменение.
- Тикеты Jira в шапке с ролями (Спринт/Бандл/РоВ) — релизная ветка и номера тикетов в
  текстах пунктов подставляются из них через `{{sprint_branch}}` и т.п., а не хардкодятся.
- Экспорт в Excel (`openpyxl`, добавлен в `requirements.txt`) в оформлении, близком к оригиналу.

Новых переменных окружения не добавилось; новые таблицы (`release_*`) создаются
автоматически при первом запуске backend'а после обновления (через `Base.metadata.create_all`,
как и раньше — миграций в проекте нет).

## Запуск на рабочей машине (Debian, без root)

### 0. Корпоративный SSL-сертификат (если сеть через прокси с подменой сертификата)

Если `pip`/`npm` ругаются на `SELF_SIGNED_CERT_IN_CHAIN` — см. раздел «Корпоративный SSL-сертификат» ниже перед установкой зависимостей.

### 1. Backend

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Откройте `backend/.env` и заполните:
- `JIRA_BASE_URL` — адрес вашей Jira (без слэша в конце)
- `JIRA_USERNAME` / `JIRA_PASSWORD` — логин и пароль
- `JIRA_JQL` — при необходимости поменяйте JQL (по умолчанию — ваши задачи, `assignee = currentUser()`)

Запуск сервера:

```bash
uvicorn app.main:app --reload --port 8000
```

Проверка: откройте в браузере `http://localhost:8000/api/health` — должно вернуть `{"status":"ok"}`.

### 2. Frontend

В новом терминале:

```bash
cd frontend
npm install
npm run dev
```

Откройте `http://localhost:5173`.

### 3. Проверка функциональности

1. Нажмите кнопку «Обновить» — должна пройти синхронизация с Jira (первый раз может занять какое-то время).
2. Если появилась красная плашка с ошибкой — пришлите текст ошибки, это поможет быстро найти причину (неверный URL, логин/пароль, некорректный JQL и т.д.).
3. Проверьте, что появился список задач в работе, отсортированный по дате обновления.
4. Разверните у одной из задач блок «Описание» и «Комментарии» — проверьте, что данные подтягиваются корректно.
5. Проверьте плитки статистики сверху (всего выполнено / год / месяц / неделя) — сверьте примерно с тем, что ожидаете увидеть.

Напишите, что получилось — пойдём дальше по итогу.

## Корпоративный SSL-сертификат (SELF_SIGNED_CERT_IN_CHAIN)

Ошибка означает, что корпоративный прокси подменяет HTTPS-сертификаты, а npm/pip/requests им не доверяют. Root-доступа нет, поэтому системный `update-ca-certificates` не подойдёт — настраиваем доверие на уровне пользователя.

**1. Получить корневой сертификат в формате PEM.** Самый надёжный способ — попросить его у ИТ/безопасности (обычно файл вида `corp-root-ca.pem` / `.crt`). Если так быстрее не получить, можно вытащить его из уже работающего браузера:

- Firefox (у него свой отдельный набор доверенных сертификатов, root не нужен): Настройки → Приватность и защита → Сертификаты → Просмотр сертификатов → вкладка «Центры сертификации» → найти сертификат с именем компании/прокси → Экспорт → сохранить как `.pem`.
- Либо через терминал (вытащит сертификат, которым прокси подписывает соединение):

  ```bash
  mkdir -p ~/certs
  echo | openssl s_client -connect registry.npmjs.org:443 -showcerts 2>/dev/null \
    | awk '/-----BEGIN CERTIFICATE-----/{c++} c==2' > ~/certs/corp-root-ca.pem
  ```

  (берём второй сертификат в цепочке — обычно это и есть корпоративный корневой/промежуточный; если файл пустой, пришлите вывод — разберёмся вручную)

**2. Настроить npm (без root, пишет в `~/.npmrc`):**

```bash
npm config set cafile ~/certs/corp-root-ca.pem
```

**3. Настроить pip (если `pip install` тоже упадёт с той же ошибкой):**

```bash
pip config set global.cert ~/certs/corp-root-ca.pem
```

Для похода backend'а в саму Jira это не нужно — там проверка SSL-сертификата отключена намеренно (`session.verify = False` в `jira_client.py`), так же как в других инструментах, которые уже работают с этой Jira.

**4. Повторить `npm install` / `pip install`.**

Быстрый небезопасный обход (если сертификат сейчас недоступен, только чтобы не блокироваться):

```bash
npm config set strict-ssl false
```

Потом стоит вернуть `npm config set strict-ssl true` и настроить нормально через cafile.
